# TODO / Известные недостатки chat_service

Обзор кода `chat_service` (модели, репозитории, сервисы, WS, инфраструктура). Ничего не менялось в коде — только список того, что стоит доработать.

## Тесты и CI

- [ ] **Нет CI-воркфлоу.** В `.github/workflows/` есть `ci-auth-service.yml`, `ci-table-service.yml`, но `ci-chat-service.yml` отсутствует — lint/tests для сервиса никогда не гоняются автоматически. `сi-integration-tests.yaml` тоже не знает про chat_service.
- [ ] **"Тесты" — это не pytest-тесты.** `chat_service/tests/test_connection_manager.py` и `test_ws.py` — обычные скрипты с `asyncio.run(main())` на уровне модуля и `print(...)`, а не `pytest`-функции с фикстурами. При запуске под `pytest` они либо не соберутся как тесты, либо выполнятся как побочный эффект импорта — падение не даст нормального repport. `test_ws.py` вообще интерактивный (`input()`), это ручной manual-скрипт, а не автотест.
- [ ] **Тесты лежат не там, где остальные.** По конвенции репозитория (см. корневой `CLAUDE.md`) юнит-тесты живут в `tests/unit/<service>/...` и импортируются из корня. `chat_service/tests/` — отдельная, непоследовательная структура; `pytest tests/unit/chat_service` ничего не найдёт.
- [ ] **`pytest`/`pytest-asyncio` не объявлены в `chat_service/requirements.txt`.** Даже если бы тесты были нормальными, зависимость для их запуска нигде не зафиксирована.
- [ ] **Нет покрытия бизнес-логики.** Нет тестов на `ChatService` (send_message, get_dialogs, mark_chat_as_read, search_users), `ChatRepository`, `UserEventConsumer`, ES fallback-логику, `RedisPubSub` тикеты — покрыт только `ConnectionManager`, и то не через pytest.

## Транзакции и слои (Repository/Service)

- [ ] **`UserRepository.upsert` / `mark_deleted` сами вызывают `session.commit()`** (`app/repository/user_projection.py`). Это нарушает слоистость, принятую в проекте («держите бизнес-логику и управление транзакциями вне репозиториев» — см. корневой `CLAUDE.md` про table_service, тот же принцип напрашивается и здесь) и не совместимо с `UnitOfWork`, которым управляются остальные репозитории (`ChatRepository`). Из-за прямого `commit()` этот репозиторий нельзя переиспользовать внутри общей транзакции с другими изменениями.
- [ ] **`UnitOfWork` не содержит `UserRepository`.** `UserEventConsumer` создаёт `UserRepository` вручную поверх сырой `AsyncSessionFactory`, в обход `UnitOfWork` — два разных способа работы с сессией в одном сервисе.
- [ ] **Гонка при создании чата.** В `ChatService.send_message` сначала `get_chat_by_users`, потом (если нет) `create_chat` — при двух параллельных первых сообщениях оба запроса не увидят чат и оба попытаются вставить строку; на `UniqueConstraint("user1_email","user2_email")` вторая вставка упадёт `IntegrityError`, которая никак не перехватывается и уйдёт наверх как необработанный 500.
- [ ] **Отправитель не проверяется.** `send_message` проверяет, что получатель существует и активен (`receiver.is_active`), но не проверяет, что сам отправитель уже есть в локальной проекции `chat_users` (FK `messages.sender_email -> chat_users.email`). Если проекция ещё не успела синхронизироваться (задержка consumer'а, см. `CLAUDE.md`), вставка сообщения упадёт по внешнему ключу — тоже необработанный 500 вместо понятной 4xx-ошибки.

## Обработка ошибок

- [ ] **Нет глобальных exception-handler'ов.** В отличие от table_service (`register_exception_handlers` в `main.py`), chat_service вообще не регистрирует обработчики — любое исключение, не являющееся `ChatException`/`HTTPException` (IntegrityError, ES/Redis ошибки и т.д.), долетает до дефолтного обработчика FastAPI как голый 500 без структурированного тела ответа.
- [ ] **`UserNotFoundException`/`UserBlockedException` принимают `email: str = None`** без `Optional[str]` — несоответствие тайп-хинта (mypy/ruff должны на это ругаться), хотя `None` реально передаётся по умолчанию.

## Elasticsearch / поиск

- [ ] **Несогласованный регистр email при поиске.** Индекс `chat_users` хранит `email` как `keyword` без нормализатора (`"normalizer": None`), то есть точное сравнение регистрозависимо. В `search_by_email_prefix` префикс пользователя не приводится к нижнему регистру (`{"prefix": {"email": prefix}}`), а исключаемый email — приводится (`exclude_email.lower()`). Если реальные email в индексе хранятся не в одном регистре (а email из событий `auth_service` кладутся as-is, без `.lower()` в `UserEventConsumer._dispatch`), поиск и/или исключение текущего пользователя будут работать непредсказуемо.
- [ ] **`ElasticsearchClient.is_available()` нигде не используется** — мёртвый код; сервис везде просто ловит исключение из `search`/`index` в момент использования, отдельная проверка доступности не нужна либо должна использоваться (например, в `/health/`).
- [ ] **Health-check сервиса не учитывает ES/Redis/RabbitMQ.** `/health/` всегда возвращает `{"status": "ok"}`, даже если ES, Redis pubsub или RabbitMQ-коннекшн упали при старте (`ensure_index()` в `lifespan` просто логирует ошибку и продолжает). Docker healthcheck будет зелёным, даже когда поиск/realtime не работают.
- [ ] **Индекс ES не обновляется при `first_name`/`last_name`, если событие `user.updated` их не содержит** — `body.get("first_name")`/`body.get("last_name")` без явного значения по умолчанию затирают предыдущие значения на `None -> ""` при частичном апдейте пользователя в auth_service.

## WebSocket / realtime

- [ ] **Нет heartbeat/ping-pong для WS-соединений.** `chat_websocket` просто крутит `await websocket.receive_text()` — «мёртвые» соединения по сети (без TCP FIN) не будут обнаружены до первой попытки `send_json` в `ConnectionManager.send_to_local`. При малом трафике зависшие соединения могут висеть в памяти долго.
- [ ] **`connection_manager` — глобальный синглтон в памяти процесса**, что осознанно (см. комментарий в `connection_manager.py`), но в `dispatch_event`/`redis_pubsub.listen` каждая реплика получает **все** события чата через один общий Redis-канал `chat:events`, а не через каналы/паттерны по конкретным пользователям — при росте числа реплик и сообщений это O(N) широковещательных доставок на реплику, из которых используется только адресованная получателю часть.
- [ ] **WS-тикет одноразовый и короткоживущий (300 c), но нет ограничения по количеству одновременных тикетов на пользователя** — `issue_ws_ticket` можно дергать многократно без rate-limit на уровне бизнес-логики (на Traefik есть общий `ratelimit@file`, но это не то же самое, что ограничение конкретно тикетов).
- [ ] **Разрыв аутентификации WS vs REST.** `/chat/ws-ticket` защищён `jwt-auth@file` (значит и `X-User-Email` подставляется Traefik), а сам `/chat/ws` — нет (аутентификация только через одноразовый тикет). Это осознанное архитектурное решение (WS не может нести заголовки), но нигде не задокументировано ограничение TTL/некст-шагов на случай, если тикет украден в течение 300 секунд — CSRF/replay для WS не рассматривается.

## Конфигурация и деплой

- [ ] **`GunicornConfig` в `settings.py` не используется.** В `Dockerfile` CMD напрямую вызывает `uvicorn` с одним воркером, `gunicorn`/`gunicorn[uvicorn]` даже не в `requirements.txt` — мёртвый конфиг-класс с `WORKERS`, `TIMEOUT`, который вводит в заблуждение (кажется, что сервис запускается через gunicorn, как остальные, но это не так).
- [ ] **`--reload` в продовом образе.** `CMD ["uvicorn", "chat_service.main:app", ..., "--reload"]` — режим для разработки (autoreload при изменении файлов) остаётся и в собранном Docker-образе, который используется в docker-compose «прод»-стеке; в `docker-compose.yaml` вдобавок примонтирован `./chat_service:/app/chat_service` как volume, то есть контейнер фактически всегда в dev-режиме.
- [ ] **`EXPOSE 8000` в Dockerfile, а реальный порт — 8002** (задаётся только в CMD/`docker-compose.yaml`/Traefik-лейблах). `EXPOSE` не влияет на рантайм, но вводит в заблуждение при чтении Dockerfile.
- [ ] **`model_config.env_file=[".env.development", "local.env"]`** — жёстко зашитые имена файлов для локальной разработки остаются в конфиге, который поедет и в продакшен-образ; не страшно (переменные окружения из compose всё равно приоритетнее), но несогласованно с остальными сервисами, где `env_prefix`/схема имён более явная (`EXCEL_APP__...` у table_service).
- [ ] **Нет `ES_INDEX_USERS`-миграции/версионирования маппинга** — если поменять `USERS_INDEX_MAPPING`, `ensure_index()` только создаёт индекс, если его нет; обновить маппинг существующего индекса некому (нет alias/reindex стратегии).

## API / схемы

- [ ] **`PaginatedResponse.items: list[MessageOut | DialogOut]`** — одна схема используется для двух совершенно разных списков (сообщения и диалоги), при этом эндпоинт диалогов (`GET /chat/users`) вообще не оборачивается в `PaginatedResponse` и возвращает голый `list[DialogOut]` — то есть `PaginatedResponse` с `DialogOut` в объединении сейчас не используется нигде, только сбивает OpenAPI-схему (Union в `items`).
- [ ] **`page`/`cursor` в `PaginatedResponse` всегда `None`.** Поля объявлены, но `ChatService.get_messages` их не считает (пагинация фактически только `limit`/`offset`, `total` есть, а `page`/`cursor` — заглушки, которые вводят в заблуждение потребителя API).
- [ ] **`GET /chat/users/search` не документирует», что поиск работает только при `len(prefix) >= 2`** (обрезается в `ChatService.search_users`, `Query(..., min_length=1, ...)` в эндпоинте) — минимальная длина в схеме (`min_length=1`) не совпадает с реальным ограничением сервиса (2), путаница для клиента фронтенда.

## Прочее

- [ ] **`role.split(".")[-1].lower()` в `UserEventConsumer._dispatch`** — хрупкий парсинг: код предполагает, что `auth_service` шлёт роль в виде `"UserRole.ADMIN"` (repr Python enum). Любое изменение формата сериализации роли в auth_service тихо сломает эту логику без явной ошибки (пустая строка/некорректная роль).
- [ ] **`ChatUser.role` ни на что не влияет** в текущей бизнес-логике chat_service (нет ни одной проверки роли) — неясно, для чего эта денормализация вообще нужна сейчас; либо мёртвое поле, либо недокументированная заготовка под будущий функционал.
