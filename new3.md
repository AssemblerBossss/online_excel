# Permission denied на JWT private key после хардненинга auth_service Dockerfile

## Симптом

После оптимизации `auth_service/Dockerfile` (уменьшение размера образа) логин стал падать 500-й:

```
PermissionError: [Errno 13] Permission denied: '/run/secrets/jwt_private.pem'
```

## Root cause

Dockerfile теперь запускает процесс не от `root`, а от отдельного пользователя:

```dockerfile
RUN groupadd -r appuser && useradd -r -g appuser appuser
...
USER appuser
```

Внутри контейнера это `uid=999(appuser) gid=999(appuser)` (конкретное число не гарантировано между сборками —
`useradd -r` берёт первый свободный system uid).

Ключ монтируется bind-mount'ом из docker-compose:

```yaml
volumes:
  - ./keys/jwt_private.pem:/run/secrets/jwt_private.pem:ro
```

а bind-mount **проецирует права хоста как есть**. На хосте:

```
-rw-------  1 mihail mihail 1704 jwt_private.pem   # 600, владелец uid 1000
-rw-rw-r--  1 mihail mihail  451 jwt_public.pem     # 644, поэтому публичный ключ и не сломался
```

`appuser` (uid 999) — не владелец и не в группе `1000`, поэтому `Permission denied`. Раньше это маскировалось тем, что
процесс шёл под `root`, который права доступа не проверяет вообще.

## Проверено и отброшено

- **`docker compose secrets:` (не-Swarm)** — протестировал локально (`docker compose` v2.40, Swarm неактивен): top-level
  `secrets:` с `file:`-источником — это тот же bind-mount с правами хоста, никакой магии с правами не происходит. Не
  решает проблему.
- **Настоящий Docker Swarm secrets** — решил бы (файлы монтируются в tmpfs с mode 0444/root), но означает переезд на
  `docker stack deploy`, отдельная история.

## Как это устроено в k8s (для сравнения)

В `k8s/base/apps/auth-service/deployment.yaml` тот же ключ монтируется через `secret`-volume:

```yaml
volumes:
  - name: jwt-keys
    secret:
      secretName: jwt-keys
```

k8s Secret-volume монтируется kubelet'ом в отдельный tmpfs с **`defaultMode: 0644`** по умолчанию (владелец
`root:root`), **независимо** от того, что лежит в манифесте — это не проекция host-прав, а собственное монтирование.
Поэтому там `appuser` спокойно читает файл без каких-либо доп. настроек (`fsGroup`/`defaultMode` в манифесте вообще не
заданы). Это единственная причина, почему тот же класс бага не стреляет в k8s.

## Варианты решения (когда дойдут руки)

1. **ACL на хостовый файл** (точечно, без ослабления остальных прав):
   ```bash
   setfacl -m u:999:r keys/jwt_private.pem
   ```
   Минус: uid контейнера не зафиксирован, может измениться при пересборке образа.

2. **Зафиксировать UID/GID в Dockerfile + chown/chmod на хосте**:
   ```dockerfile
   RUN groupadd -r -g 10001 appuser && useradd -r -g appuser -u 10001 appuser
   ```
   ```bash
   sudo chown :10001 keys/jwt_private.pem && chmod 640 keys/jwt_private.pem
   ```

3. **`chmod 644 keys/jwt_private.pem`** — самый простой вариант. Формально даёт world-read на приватный ключ, но по
   факту не отличается от того, что уже происходит в k8s (там тот же ключ смонтирован с 0644) — так что для local dev
   это не понижение реального уровня защиты.

4. **Быстрый костыль на сейчас**: убрать `USER appuser` из Dockerfile, вернуться на root. Работает сразу, ничего не
   трогает на хосте, но откатывает хардненинг образа — не забыть вернуться к non-root user, когда будут решены права на
   секреты.

## Отдельная (более срочная) находка — не откладывать

`k8s/base/jwt-keys.yaml` с настоящим PEM приватного ключа был закоммичен в `9018b0d` и хоть потом убран из индекса (
`2843077`), **история не переписывалась** — коммит `9018b0d` уже есть на `origin/main` и ещё трёх ветках на GitHub. Ключ
нужно считать скомпрометированным независимо от того, какой вариант выше выбран:

- сгенерировать новую пару RSA для JWT (private+public),
- обновить `jwt-keys` Secret в k8s и `keys/jwt_private.pem` / `keys/jwt_public.pem` локально,
- опционально почистить git-историю (`git filter-repo`/BFG + force-push) — но это не отменяет необходимость ротации,
  т.к. уже сделанные клоны/форки ключ сохранили.

● Смотря честно на объём — это не мелкая доработка поверх текущего, а по сути отдельный PR сопоставимого размера с фазой
1, плюс presence — целиком новая фича. Из этого ничего не выбрасывается, большая часть фазы 1 переиспользуется как есть.

Что переиспользуется без изменений:

- DataService.create_table_row/update_table_row/delete_table_row — вся бизнес-логика (permission-check, валидация,
  доменные исключения) уже в сервисном слое, транспорт-агностична.
- RowEventPublisher / Redis Pub/Sub / TableWsManager.broadcast — фан-аут между репликами не меняется, событие после
  мутации по WS публикуется точно так же, как сейчас после REST.
- Тикет-аутентификация на подключение — остаётся, просто личность юзера с этого момента нужно держать привязанной к
  сокету на весь его срок жизни (а не только в момент connect()).

Что придётся сделать нового:

1. Протокол сообщений (сейчас его физически нет — websocket.receive_text() в ws.py просто ждёт разрыва и выкидывает всё,
   что придёт). Нужен конверт с корреляцией запрос/ответ:
   client → {type: "row.update", request_id, table_id, row_id, payload}
   server → {type: "ack"|"error", request_id, data|detail}
1. плюс отдельно — уже существующие push-события row.created/updated/deleted для остальных клиентов.
2. Привязка user к соединению. TableWsManager._connections сейчас dict[table_id, set[WebSocket]] — без информации, кто
   есть кто. Нужно расширить до dict[table_id, dict[WebSocket, SUserFilter]] (или отдельный registry), чтобы на каждое
   входящее сообщение знать user_id/role для
   permission_service.check_write_access, без повторной аутентификации по тикету на каждое сообщение.
3. Диспетчер в ws.py. Внутри while True: msg = await websocket.receive_json() — парсинг типа, вызов соответствующего
   метода DataService, оборачивание доменных исключений в {"type": "error", ...} вместо HTTP-хендлеров из main.py (их
   логику десериализации ошибок нужно продублировать/переиспользовать для
   WS-ответов).
4. Фронт: RPC поверх WS. ws.ts сейчас только слушает. Нужен слой с request_id + Promise-обёрткой (send(type, payload):
   Promise<Ack>), и TableViewPage.tsx (commitEdit, addRow, deleteRow) переключить с tablesAPI.* на этот RPC. Отдельный
   вопрос — fallback на REST, если сокет в данный момент
   разорван/переподключается (иначе любой пользователь с нестабильным соединением не сможет редактировать вообще). Это
   отдельная развилка: либо гибрид (пробуем WS, при недоступности — HTTP), либо блокируем UI до реконнекта.
5. Presence — с нуля, самая большая часть. Ничего похожего сейчас нет:
   - новые типы событий presence.join/leave, возможно cursor/editing_cell;
   - хранение состояния "кто сейчас в таблице" — по аналогии с events:rows:{table_id} нужен ещё один
   Redis-канал/структура (presence:{table_id}, Set с TTL или heartbeat, т.к. реплик несколько — то же самое требование к
   фан-ауту, что и у row-событий);
   - UI-часть (аватарки/курсоры других пользователей) — фронтенд-работа, которой пока нет вообще.
6. Конфликты одновременного редактирования. Сейчас нет никакой версионности (ни в REST, ни в модели TableRow) —
   last-write-wins. С мгновенным WS-редактированием конфликты станут заметнее (два юзера правят одну ячейку почти
   одновременно). Не обязательно для MVP фазы 2, но стоит заложить хотя бы
   updated_at-based optimistic check, иначе фаза 2 будет казаться более "глючной", чем нынешний REST.
7. Тесты. Текущий интеграционный тест (websockets-клиент получает row.created при REST-мутации) нужно дополнить
   симметричным сценарием — мутация приходит по WS, ack корректный, второй клиент получает push; плюс тест на отказ
   доступа прямо в WS-диспетчере.

Грубая прикидка по кускам, от простого к сложному:

- пп. 1–3 (протокол + диспетчер + user-registry) — переиспользует всю существующую бизнес-логику, самый дешёвый кусок;
- п. 4 (фронт RPC + fallback) — средний, основная сложность в решении про поведение при разрыве соединения;
- п. 6 (конфликты) — можно отложить дальше, не блокирует остальное;
- п. 5 (presence) — по объёму сопоставим с пп. 1–4 вместе взятыми, и это чистый feature-add, а не рефакторинг
  существующего.

Если будете делать — пп. 1–4 имеет смысл вынести в отдельный PR3 (мутации по WS с REST-фолбэком), а presence — в
отдельный PR4, это разные по риску вещи и тестировать их вместе неудобно.
